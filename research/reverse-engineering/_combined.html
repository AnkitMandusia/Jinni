Top findings that should actually change decisions

  1. Jinni's checkout is more complete than a surface scan suggested. Coupons and a payment-method picker (COD/UPI with server-side verification) both already work. Don't rebuild these — the real gaps are narrower: serviceability pre-checking and structured OOS/substitution handling (currently a free-text note to the store).

  2. Jinni's order model is architecturally different from Zepto's, on purpose. Zepto pre-resolves a single dark store by location before checkout. Jinni broadcasts orders to nearby stores to accept (race-to-accept). This isn't a gap to close — it's a different design that changes what "is this address serviceable" even means here. Any serviceability-check feature needs to be designed for Jinni's model, not copied from Zepto's.

  3. Jinni is one codebase serving five roles (customer/admin/store/partner-shared), routed at the root navigator by user role and status. Zepto is consumer-only; its store/delivery-partner experiences are separate products. This is a real tradeoff (unified maintenance vs. bundle size and permission surface) worth being deliberate about as the app grows, not something to reassess by accident later.

  4. Cab and salon are live, not scaffolding. enabled: true in the module registry, right now. If your near-term focus is genuinely grocery+food, worth an explicit decision about whether cab/salon get resourced too or stay parked — the code doesn't currently signal which.

  5. Zepto carries features outside grocery scope (pharmacy with prescription upload/consent, electronics trade-in, festival campaign UI) — explicitly NOT recommended to replicate per your own instruction to design original architecture, not copy Zepto feature-for-feature.

Method & confidence caveat (OBSERVED methodology, read first)

Extracted via regex SCREEN_VIEWE?D_[A-Z0-9_]+ directly against the Hermes bytecode's raw text. Hermes packs string-table entries back-to-back with NO delimiter in this raw-byte view, so many matches "bleed" into the next adjacent constant (e.g. SCREEN_VIEWED_CART_PAGE_KEY + the next string SCREEN_VIEWED_HOME_PAGE... show up concatenated). The list below is manually cleaned to the real left-hand token where the boundary is unambiguous (usually at _PAGE, _BS, _MODAL, or a clear second SCREEN_VIEWED_ prefix). Treat each entry as INFERRED to be a real analytics screen-view event name; none of this is confirmed against actual navigation/route code, since no Hermes disassembler was available to recover the call sites that fire these events (see Phase 2 findings doc for the tooling gap). Jinni — Phase 5: Technical Architecture Findings (superapp-mobile)

All OBSERVED — read directly from source files in E:\work\super\superapp-mobile\src.

State management

  • Zustand throughout, via two factory helpers in shared/store/useStore.ts:
  • createStore — plain store with devtools middleware only
  • createPersistedStore — adds persist middleware backed by AsyncStorage (custom storage adapter, JSON-serialized), a partialize step that strips transient fields (isLoading, error) from what gets persisted, and an onRehydrateStorage hook
  • Special case: the auth store's rehydration hook calls setApiToken() to warm the API client's in-memory token cache immediately on cold start, avoiding an AsyncStorage round-trip on the first request
  • Per-module stores follow this same pattern consistently: cartStore, groceryStore, orderStore, authStore, locationStore all use one of the two factories
  • Minor cleanup item (not urgent): createPersistedStore has several console.log debug statements left in (store creation, storage reads, rehydration status) — fine for dev, worth stripping or gating behind __DEV__ before a release build

Cart architecture

  • Single unified cart store (modules/cart/store/cartStore.ts) shared across ALL verticals (food, grocery, cab, salon), not per-module carts. Each CartItem carries its own moduleType and sourceId/sourceName (restaurant or store).
  • Cross-source conflict handling: addItem() returns {ok: false, needsConfirm: true, ...} if the cart already has items from a different restaurant/store IN THE SAME module type, requiring the caller to explicitly call forceAddItem() to replace that module's items. This is the single-cart equivalent of what many single-vertical apps (including, per Phase 1-4 evidence, likely Zepto) handle by just locking the cart to one store — Jinni's version is more general since it has to coexist with 3 other verticals in the same store.
  • Per-module derived totals (getFoodTotal, getGroceryTotal) exist on the shared store rather than each module computing its own — keeps a single source of truth.

API / networking layer

  • Single Axios instance (shared/services/api.ts), REST only, base path /api/v1 against a FastAPI-style backend (consistent with your profile: FastAPI/PostgreSQL backend).
  • Auth token handling: in-memory _tokenCache warmed on login/refresh/rehydration, with AsyncStorage as fallback for cold-start before the store rehydrates. JWT validity is sanity-checked by segment count (3 dot-separated parts) before use.
  • 401 handling: response interceptor catches 401, attempts a refresh-token exchange exactly once (_retry flag guards against infinite loop), updates the in-memory cache before retrying the original request, and on refresh failure clears all auth storage and calls a registered onAuthFailure callback — this callback indirection avoids a circular import between api.ts and authStore.
  • No request-level retry/backoff beyond the single 401-refresh retry; no offline request queue observed in this file (would need to check elsewhere if that's a requirement).

Navigation

  • React Navigation (native-stack). RootNavigator is role-based, not just authenticated-vs-not: it inspects user.role and user.status to route into one of FIVE distinct navigators — Auth, Main (customer), Admin, Store (store-owner), Partner (covers restaurant/delivery/cab_driver/salon roles with one shared navigator).
  • This is architecturally distinct from Zepto: Zepto (per Phase 1 manifest findings) is a single-role consumer app; store and delivery-partner experiences are presumably separate apps/products. Jinni is ONE codebase serving customer + admin + store + all partner types, routed by role at the root. This is a significant design decision with real tradeoffs (single codebase to maintain and ship vs. bundle size / permission surface covering all roles in one build) worth being deliberate about rather than incidental.
  • isFullySetup gates on profile_complete AND role being set, with a distinct pending_approval status screen — suggests partner/store roles go through a manual-approval step before activation, unlike customer signup.

Module architecture

  • Static module registry (modules/moduleRegistry.ts): food, grocery, cab, salon are all enabled: true RIGHT NOW — confirmed NOT dormant scaffolding. Jinni is actively a 4-vertical super-app today, not grocery+food with extra folders. Worth flagging explicitly since it's broader than your original research brief's framing ("grocery-commerce and food-delivery application") — may be worth a scope conversation about whether cab/salon share your roadmap priority or are earlier-stage/parked work.
  • Each module supplies a HomeCard component (home screen vertical switcher tile) and a navigator (its own stack) — consistent, pluggable pattern. Static imports are used deliberately ("Metro compatibility" per inline comment) rather than dynamic require/lazy-loading, which is a reasonable tradeoff for a 4-module app but would need revisiting if more verticals are added (bundle size grows linearly with every module, always included, never code-split).

Order model (carried over from Phase 7 note, included here for completeness)

  • Grocery orders use a "race-to-accept" broadcast model: order is placed generically via POST /orders, backend notifies nearby stores to accept — no store pre-selected by the customer at checkout. This is a deliberate architectural choice distinct from Zepto's single-resolved-dark-store model, with implications for Phase 5 serviceability-check design (per Phase 7 gap analysis): "is this address serviceable" in Jinni's model means "will any nearby store accept this", which is a different (harder) guarantee to give the customer upfront than Zepto's "this specific store will fulfill it."

MAJOR CORRECTION: "Order with Jinni" AI ordering assistant is REAL, not a stub

Initial read of OrderWithJinniButton.tsx (food module) suggested this was UI-only, per its own code comment: "functional food pre-load (search_food / add_items_to_cart tools) is backend work tracked separately; this wires the UI entry point and context hint only."

Opening useJinniSession.ts and interpretService.ts (jinni module) shows this comment is STALE — the feature is substantially built and functioning end-to-end:

  • Voice session lifecycle: open -> listening -> submitWish -> thinking -> results -> confirmAddToCart -> success, with server-tracked sessions (startSession/cancelSession/ completeSession) and a rate-limited "wishes" quota (server-enforced via HTTP 429, with a client-side isExhausted check as a fast-path, refreshed from server state) — the genie/"Chirag" persona theme is carried through a named phrase system and TTS.
  • Real backend intent interpretation: interpretService.ts's own comment confirms hardcoded demo catalogs were explicitly REMOVED from the production path.   • Local-first UX, server-authoritative data: a local keyword matcher (JinniIntentFinder) gives instant UI feedback and a confidence hint sent to the backend, but is explicitly never trusted as a source of truth — on backend failure, the code deliberately surfaces a clarification message rather than fabricating items from the local match. This is a notably careful anti-hallucination design choice.
  • Real cart integration: confirmAddToCart builds real cart lines and reuses the exact same cross-source conflict pattern (addItem / forceAddItem) documented in jinni-technical-architecture.md for the shared cart store — this isn't a parallel path, it feeds the same cart everything else uses.
  • TTS safety rule (explicit in code comment): the app is only ever allowed to SPEAK pre-scripted phrases, never dynamic AI-generated text, product names, prices, or order details out loud — a deliberate guard against reading untrusted/hallucinated content aloud. Good practice worth preserving as this feature grows.
